Populating NGSO-to-GSO inputs

How to fill in a parameter file for sharc/ngso_to_gso.py, based on the example in scenarios/scenario_base.yaml (USASAT-NGSO-8 into Ku/Ka-band GSO links over Las Vegas, Kansas and Miami).

branch feat/multiconstellation_support format version 2 schema: ngso2gso_params.schema.json

Overview

The simulator reads only the ngso2gso section of the YAML file. Other top-level keys are ignored, which is why the example keeps its reusable link and place definitions under gso_links_helpers as YAML anchors. Inside ngso2gso, any key the code does not know about stops the run with The parameter … was passed, but it doesn't exist on parameters definitions!

ngso2gso:
  version, scenario_name, seed            # identity and RNG
  delta_t_s, min_t_s, max_t_s, batch_size # time stepping
  ref_bandwidth_Hz                        # noise and PFD reference bandwidth
  minimum_elevation, selection_strategy   # defaults for every NGSO system
  ngso_systems:                           # list: one per operator
    - label, n_co_channel, gso_protection_avoidance_angle
      selection_strategy?, minimum_elevation?, center_freq_GHz?, bandwidth_MHz?
      tx_model: { model, pfd_at_ref_bandwidth_dBW_m2 }
      orbits:                             # list: one per shell
        - n_planes, sats_per_plane, inclination_deg, perigee_alt_km, apogee_alt_km, phasing_deg, …
  gso_links:                              # list: one per victim link × location
    - label, orbital_slot_deg, center_freq_GHz, bandwidth_MHz, eirp_dBW_per_carrier,
      peak_rx_antenna_gain, rx_antenna_size_m, g_over_t_dB_per_K, station_type, added_loss
      earth_station: { label, lat_deg, lon_deg, alt_m? }

A minimal runnable file

One NGSO system with one shell, one victim link at one location. Values come from the example; max_t_s is shortened for a quick test. The same file is shipped as exemplo_minimo.yaml, together with exemplo_completo.yaml, exemplo_multiplos_sistemas.yaml and exemplo_ancoras.yaml. The last one is the full example written with YAML anchors (&name, *name, <<: *name) so each link and location is defined once; the merge key << is YAML 1.1 and some strict YAML 1.2 readers reject it.

ngso2gso:
  version: 2
  scenario_name: quick_test
  seed: 125
  delta_t_s: 1.0
  min_t_s: 0.0
  max_t_s: 1000.0
  batch_size: 500
  ref_bandwidth_Hz: 1000000
  minimum_elevation: 35.0
  selection_strategy: RAND

  ngso_systems:
    - label: USASAT-NGSO-8
      n_co_channel: 8
      gso_protection_avoidance_angle: 2.0
      tx_model:
        model: CONSTANT_PFD_AT_GND
        pfd_at_ref_bandwidth_dBW_m2: -115.0
      orbits:
        - n_planes: 289
          sats_per_plane: 4
          inclination_deg: 51.9
          perigee_alt_km: 630.0
          apogee_alt_km: 630.0
          phasing_deg: 71.09

  gso_links:
    - label: Jupiter 97W GW
      orbital_slot_deg: -97.1
      center_freq_GHz: 20.075
      downlink_freq_MHz: [19700, 20200]
      bandwidth_MHz: 250.0
      eirp_dBW_per_carrier: 71.0
      peak_rx_antenna_gain: 62.0
      rx_antenna_size_m: 6.3
      g_over_t_dB_per_K: 38.0
      station_type: GW
      added_loss: 3.0
      earth_station:
        label: Miami
        lat_deg: 25.77
        lon_deg: -80.19

ngso_systems[]: one entry per NGSO operator

Each system picks its own n_co_channel satellites independently at each time step, shared across all its shells. Interference from all systems is power-summed at the earth station, and results also get per-system columns i---<label> and epfd---<label>.

orbits[]: one entry per shell

Validation rules

The JSON schema covers most of these. The ones marked "load time only" need comparisons between fields and are checked by validate() when the file is loaded.

  • selection_strategy is set but version is missing or below 2.ValueError: AOPASA
  • The file still uses the old single-system ngso2gso.ngso key.Migrate with: python scenarios/migrate_to_ngso_systems.py <file>
  • Only one of center_freq_GHz / bandwidth_MHz is set on an NGSO system.set both center_freq_GHz and bandwidth_MHz, or neither
  • An NGSO system label contains ---, or two systems share a label.
  • Two GSO links share both label and earth_station.label (load time only).More than one GSO Earth Station has the same label
  • max_t_s ≤ min_t_s, or apogee_alt_km < perigee_alt_km (load time only).
  • gso_links is null or empty, which is the state of the committed base file.
  • YAML values like 2 and 2.0 are both accepted for float fields. Integer fields (n_co_channel, n_planes, sats_per_plane, batch_size, seed) should be written without a decimal point.

What the inputs control

At each time step, for each GSO link, the code propagates every shell, keeps satellites above minimum_elevation and outside the avoidance angle, selects n_co_channel per system with its strategy, applies the PFD and the earth station's off-axis gain, scales by band overlap, and sums. The carrier C comes from eirp_dBW_per_carrier − 10·log10(bandwidth_MHz) + peak_rx_antenna_gain − added_loss − free-space loss − rain attenuation; noise from G/T and ref_bandwidth_Hz.

Results go to one parquet file per GSO link, gso_per_iteration---<link>---<earth station>.parquet, under scenarios/results/<timestamp>/<scenario_name>/ (relative to where the simulation is run). Each row is one time step, with aggregate columns c, cn, cni, i, epfd, plus i---<system> and epfd---<system> per NGSO system, and gso_rain_att (rain attenuation drawn for that step, dB).
