Como preencher as entradas NGSO-para-GSO

Como montar um arquivo de parâmetros para sharc/ngso_to_gso.py, a partir do exemplo em scenarios/scenario_base.yaml (USASAT-NGSO-8 interferindo em enlaces GSO em banda Ka sobre Las Vegas, Kansas e Miami).

repo artistrea/sharc-ngso-throughput branch feat/ngso_throughput_studies formato versão 2 schema: ngso2gso_params.schema.pt-BR.json

Visão geral

O simulador lê apenas a seção ngso2gso do arquivo YAML. As demais chaves de nível superior são ignoradas, e por isso o exemplo guarda definições reutilizáveis de enlaces e localidades em gso_links_helpers, como âncoras YAML. Dentro de ngso2gso, qualquer chave desconhecida interrompe a execução com The parameter … was passed, but it doesn't exist on parameters definitions!

Chaves e valores enumerados (RAND, GW, CONSTANT_PFD_AT_GND…) ficam em inglês, como o código espera.

ngso2gso:
  version, scenario_name, seed            # identificação e gerador aleatório
  delta_t_s, min_t_s, max_t_s, batch_size # passos de tempo
  ref_bandwidth_Hz                        # banda de referência de ruído e PFD
  band_overlap, allow_zero_band_overlap   # ponderação por sobreposição (desligada por padrão)
  minimum_elevation, selection_strategy   # padrões para todos os sistemas NGSO
  ngso_systems:                           # lista: um por operador
    - label, n_co_channel, gso_protection_avoidance_angle
      selection_strategy?, minimum_elevation?, center_freq_GHz?, bandwidth_MHz?
      tx_model: { model, pfd_at_ref_bandwidth_dBW_m2 }
      orbits:                             # lista: uma por camada orbital
        - n_planes, sats_per_plane, inclination_deg, perigee_alt_km, apogee_alt_km, phasing_deg, …
  gso_links:                              # lista: um por enlace vítima × localidade
    - label, orbital_slot_deg, center_freq_GHz, bandwidth_MHz, eirp_dBW_per_carrier,
      peak_rx_antenna_gain, rx_antenna_size_m, g_over_t_dB_per_K, station_type, added_loss
      earth_station: { label, lat_deg, lon_deg, alt_m? }

Instalação e execução

Requer Python 3.12 ou mais recente e git. Clone a branch, crie um ambiente virtual, instale as dependências fixadas e depois instale o próprio repositório em modo editável, para que import sharc funcione nos scripts.

git clone --branch feat/ngso_throughput_studies https://github.com/artistrea/sharc-ngso-throughput.git
cd sharc-ngso-throughput
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install -e .

Execute a partir da raiz do repositório, passando o arquivo de parâmetros com -p. O exemplo mínimo abaixo leva poucos segundos:

python sharc/ngso_to_gso.py -p scenarios/ngso2gso_docs/exemplo_minimo.yaml

O script mostra o diretório de saída, scenarios/results/<timestamp>/<scenario_name>/, relativo ao diretório de onde é executado. Uma cópia do arquivo de parâmetros é salva ali junto com os resultados em parquet (veja O que as entradas controlam). Se uma execução com o mesmo scenario_name e arquivo de parâmetros idêntico foi interrompida, a próxima execução pergunta se deve continuá-la.

Regras de validação

O JSON schema cobre a maioria delas. As marcadas "só ao carregar" comparam campos entre si e são verificadas por validate() quando o arquivo é carregado.

  • selection_strategy definido com version ausente ou menor que 2.ValueError: AOPASA
  • O arquivo ainda usa a chave antiga de sistema único ngso2gso.ngso.Migrate with: python scenarios/migrate_to_ngso_systems.py <arquivo>
  • Apenas um de center_freq_GHz / bandwidth_MHz definido em um sistema NGSO.set both center_freq_GHz and bandwidth_MHz, or neither
  • Um sistema NGSO define center_freq_GHz/bandwidth_MHz com band_overlap em FULL (o padrão), ou allow_zero_band_overlap é true com FULL.NGSO systems [...] set center_freq_GHz/bandwidth_MHz, but ngso2gso.band_overlap is 'FULL'
  • band_overlap é FRACTION e algum sistema NGSO não tem banda.every NGSO system must set center_freq_GHz and bandwidth_MHz
  • band_overlap é FRACTION, a banda de um sistema não toca algum enlace e allow_zero_band_overlap não é true (só ao carregar).These NGSO systems do not overlap these GSO links in frequency
  • Label de sistema NGSO contendo ---, ou dois sistemas com o mesmo label.
  • Dois enlaces GSO com o mesmo label e o mesmo earth_station.label (só ao carregar).More than one GSO Earth Station has the same label
  • max_t_s ≤ min_t_s, ou apogee_alt_km < perigee_alt_km (só ao carregar).
  • gso_links null ou vazio, que é o estado do arquivo base versionado.
  • Em campos de ponto flutuante, 2 e 2.0 são aceitos. Campos inteiros (n_co_channel, n_planes, sats_per_plane, batch_size, seed) devem ser escritos sem ponto decimal. Use ponto, não vírgula, como separador decimal no YAML.

O que as entradas controlam

A cada passo de tempo, para cada enlace GSO, o código propaga todas as camadas, mantém os satélites acima de minimum_elevation e fora do ângulo de evitação, escolhe n_co_channel por sistema com a estratégia dele, aplica a PFD e o ganho fora do eixo da estação terrena, pondera pela sobreposição de banda se band_overlap for FRACTION e soma. A portadora C vem de eirp_dBW_per_carrier − 10·log10(bandwidth_MHz) + peak_rx_antenna_gain − added_loss − perda de espaço livre − atenuação por chuva; o ruído, do G/T e de ref_bandwidth_Hz.

Os resultados vão para um arquivo parquet por enlace GSO, gso_per_iteration---<enlace>---<estação terrena>.parquet, em scenarios/results/<timestamp>/<scenario_name>/ (relativo ao diretório onde a simulação é executada). Cada linha é um passo de tempo, com as colunas agregadas c, cn, cni, i, epfd, mais i---<sistema> e epfd---<sistema> por sistema NGSO, e gso_rain_att (atenuação por chuva sorteada para o passo, em dB). O arquivo band_overlap.json, na mesma pasta, registra o modo e o fator aplicado a cada par (enlace, sistema), como fração e em dB (null em dB significa sem sobreposição).
